    Request to activate one or more Market Locations.

    Activation marks the Market Location as active again for normal operations, allowing new sample ingestion and inclusion in default listings. Historical samples, revisions, and metadata remain unchanged.

    Streaming response containing one or more time series fragments.

    The service emits a distinct MarketLocationSeries message for every unique tuple of Market Location, EnergyFlowDirection and MetricType.

    The RPC is a finite server-side stream: once all samples matching the request (across all Market Locations, directions, and metric types) have been delivered, the server closes the stream. However, if the request’s time_filter specifies no end_time, the stream continues in real time.

    Consumers should treat each market location series in each streamed message as an independent, self-contained segment. Responses may be chunked.

    Incremental / Chunked Streaming

    The service may emit: • complete series in a single message, or • multiple incremental/chunked segments.

    Sample Ordering & Updates

    There is no guaranteed ordering between different series, between chunks of different series, or across series. A client MUST treat every received MarketLocationSeries as an independent, self-contained segment and merge or sort samples locally if ordering is required.

    The service may also emit more than one sample with identical sample_time. This is normal and reflects the correction workflows required in regulated metering and real-time resampling.

    A sample may be re-emitted whenever the service obtains better or newer information for that timestamp—whether through revised native readings, delayed arrivals, or updated resampling intervals.

    frequenz.api.marketmetering.v1alpha1.marketmetering_pb2.ResamplingOptions ¤

    Bases: Message

    Resampling options for Market Location time-series data.

    Resampling allows clients to request a time resolution that differs from the Market Location’s native stored resolution. The service constructs a uniform output grid based on the requested resolution and produces exactly one sample per interval.

    Two semantic modes may result:

    • Downsampling (when the requested resolution is coarser) Multiple native samples fall into one output interval; these are combined using the selected aggregation method.

    • Upsampling (when the requested resolution is finer) Each native sample expands into multiple sub-intervals. ENERGY is allocated proportionally, while POWER is repeated stepwise.

    In both cases the output sample timestamp equals the start of the interval in the materialized grid.

    Example: Downsampling from 1-minute to 15-minute intervals

    The stored time series has a native resolution of Δt = 1 minute. Resampling is requested with a resolution of ΔT = 15 minutes. In this case all native samples whose timestamps fall within an interval [t, t + Δt) contribute to the aggregated value for that interval. The timestamp of the aggregated sample is exactly t, the start of the interval.

    For each interval k: Ik = [T0 + k·ΔT, T0 + (k+1)·ΔT)

    The aggregated value A_k is the arithmetic mean of all samples whose timestamps ts satisfy: ts ∈ Ik

    The resampled series consists of points: (t = T0 + k·ΔT, value = A_k)

    Upsampling: 15-minute → 5-minute

    If the native resolution is Δt = 15 min and the requested resolution is ΔT = 5 min, each native interval expands into three equally sized sub-intervals, with ENERGY proportionally allocated and POWER repeated.

    frequenz.api.marketmetering.v1alpha1.marketmetering_pb2.UpsertMarketLocationSamplesStreamRequest ¤

    Bases: Message

    A single ingestion event for one Market Location sample.

    Each request message processes exactly one sample and produces one acknowledgement response.

    The server performs strict validation of

    • timestamp alignment with the Market Location's contractual resolution, • energy-flow direction against supported_directions, • metric_type against supported metrics, • metric_unit consistency with metric_type, • revision monotonicity for the (ML, direction, metric, timestamp) tuple.

    Correction via revisioning (no deletion)

    The MarketMeteringService never deletes samples. Regulated metering processes require a full historical audit trail.

    A previously ingested sample is corrected by submitting a new revision with the same sample_time but a higher revision value.

    Typical patterns: • Invalidate a value → send a new revision with quality = DATA_QUALITY_MISSING and value = 0. • Correct a value → send a new revision with the corrected value and quality = DATA_QUALITY_CORRECTED.

    The backend selects the highest revision when serving data, while older revisions remain queryable via revision strategies.

    Timestamp alignment is mandatory

    sample.sample_time MUST align with the Market Location's contractual time_resolution.

    Example: time_resolution = PT15M → allowed times are: 00:00, 00:15, 00:30, 00:45, ...

    Misaligned timestamps are rejected.

    Metric-unit consistency is validated

    The provided metric_unit MUST be compatible with metric_type. ENERGY → {Wh, kWh, MWh} POWER → {W, kW, MW} REACTIVE_ENERGY → {VArh, kVArh, MVArh} REACTIVE_POWER → {VAr, kVAr, MVAr}

    The backend does not perform unit conversion.

    Direction and metric must be allowed
