    ActivateMarketLocationRequest¤

    Request to activate one or more Market Locations.

    Activation marks the Market Location as active again for normal operations, allowing new sample ingestion and inclusion in default listings. Historical samples, revisions, and metadata remain unchanged.

    The operation is idempotent: requesting activation for an already active Market Location does not produce an error.

    Field Type Label Description
    market_location_refs MarketLocationRef repeated List of Market Locations to activate.

    ActivateMarketLocationResponse¤

    Response for batch activation of Market Locations.

    A Result entry is returned per MarketLocationRef, regardless of whether the operation succeeded or failed. Structured error codes allow clients to implement automated handling and retries.

    Field Type Label Description
    results MarketLocationOperationResult repeated Activation results, one per market location from the request.

    CreateMarketLocationRequest¤

    Creates a new Market Location within an Enterprise.

    A Market Location represents a contract-level metering point identifier used in regulated electricity markets (e.g., MaLo in DE, MPAN in UK, ESI-ID in US, NMI in AU). This RPC registers such a Market Location with the platform.

    !!! example "Example Request" 

    {
  &#34;market_location_ref&#34;: {
    &#34;enterprise_id&#34;: 42,
    &#34;market_location_id&#34;: {
      &#34;value&#34;: &#34;DE01234567890&#34;,
      &#34;type&#34;: &#34;MARKET_LOCATION_ID_TYPE_MALO_ID&#34;
    }
  },
  &#34;market_location&#34;: {
    &#34;display_name&#34;: &#34;Main Office – Consumption&#34;,
    &#34;market_area&#34;: &#34;MARKET_AREA_DE&#34;,
    &#34;supported_directions&#34;: [&#34;ENERGY_FLOW_DIRECTION_IMPORT&#34;],
    &#34;time_resolution&#34;: &#34;TIME_RESOLUTION_15_MIN&#34;,
    &#34;payload&#34;: {
      &#34;siteCode&#34;: &#34;HQ-North&#34;,
      &#34;comment&#34;: &#34;Primary billing meter&#34;
    }
  }
}

    Field Type Label Description
    market_location_ref MarketLocationRef Identifies the target enterprise and the Market Location ID to create.

    All fields except payload must be populated. The service performs validation and assigns revision numbers upon creation. |

    DeactivateMarketLocationRequest¤

    Request to deactivate one or more Market Locations.

    Deactivation marks each Market Location as inactive for future operations, without deleting historical metadata or time-series samples. This aligns with regulatory expectations: Market Locations must remain auditable even when they are no longer active.

    A deactivated Market Location: • cannot receive new samples, • is omitted from default listing operations (unless explicitly requested), • retains all historical revisions for audit, reporting, and compliance.

    The operation is idempotent: requesting deactivation for an already inactive Market Location does not produce an error.

    Field Type Label Description
    market_location_refs MarketLocationRef repeated List of Market Locations to deactivate.

    DeactivateMarketLocationResponse¤

    Response for batch deactivation of Market Locations.

    Each entry in results corresponds to a market location from the request and reports whether the operation succeeded, failed, or was skipped (e.g., already inactive).

    The RPC never deletes historical data; it only changes activation state.

    Field Type Label Description
    results MarketLocationOperationResult repeated Deactivation results, one per market location from the request.

    MarketLocation¤

    Represents a logical Market Location used in regulated electricity markets.

    A Market Location is a contract-level metering point identifier defined by the local jurisdiction (e.g., MaLo in Germany, MPAN in the UK, ESI-ID in the US, NMI in Australia). It abstracts from physical meters or channels and is the anchor for billing, settlement, reconciliation, forecasting, and portfolio aggregation.

    !!! example "Example Market Location Object" 

    {
  &#34;display_name&#34;: &#34;Main Office – Consumption&#34;,
  &#34;market_area&#34;: &#34;MARKET_AREA_DE&#34;,
  &#34;supported_directions&#34;: [&#34;ENERGY_FLOW_DIRECTION_IMPORT&#34;],
  &#34;time_resolution&#34;: &#34;TIME_RESOLUTION_15_MIN&#34;,
  &#34;payload&#34;: {
    &#34;cost_center&#34;: &#34;CC-1103&#34;,
    &#34;site_group&#34;: &#34;HQ-North&#34;,
    &#34;notes&#34;: &#34;Primary billing meter&#34;
  }
}

    Field Type Label Description
    display_name string Optional human-readable name for organizational use.
    market_area MarketArea Jurisdiction in which this Market Location is registered.
    supported_directions EnergyFlowDirection repeated Supported energy-flow directions for this Market Location.

    Indicates which energy-flow directions this Market Location is permitted to represent according to regulatory or contractual rules.

    !!! note "What supported_directions means" This field reflects the contractual capability of the Market Location to represent import (consumption), export (generation), or both. It does not describe physical wiring or real-time flow, but the officially registered role in the market.

    !!! examples "Market Location Examples" • Germany (DE) - Consumption MaLo → [IMPORT] - Feed-in MaLo → [EXPORT]

    • UK (MPAN) - A single MPAN may support both directions → [IMPORT, EXPORT] | | time_resolution | TimeResolution | | Primary contractual time resolution for this Market Location.

    This describes the default metering interval (e.g., PT15M, PT30M, PT5M). It reflects the settlement granularity expected by the jurisdiction.

    !!! note Some markets provide multiple resolutions. This is metadata describing the primary resolution (e.g., PT15M). | | payload | google.protobuf.Struct | | Optional user-defined metadata.

    Clients may store arbitrary structured data (e.g., cost centers, internal references, grouping labels, billing metadata). |

    MarketLocationDetail¤

    Detailed representation of a Market Location, including metadata necessary for revision management, activation state, and lifecycle tracking.

    MarketLocationDetail wraps the immutable identity fields and semantic attributes contained in MarketLocation with operational metadata.

    !!! example "Example MarketLocationDetail Object" 

    {
  &#34;market_location_ref&#34;: {
    &#34;enterprise_id&#34;: 42,
    &#34;market_location_id&#34;: {
      &#34;value&#34;: &#34;DE01234567890&#34;,
      &#34;type&#34;: &#34;MARKET_LOCATION_ID_TYPE_MALO_ID&#34;
    },
  &#34;market_location&#34;: {
    &#34;display_name&#34;: &#34;Main Office – Consumption&#34;,
    &#34;market_area&#34;: &#34;MARKET_AREA_DE&#34;,
    &#34;supported_directions&#34;: [&#34;ENERGY_FLOW_DIRECTION_IMPORT&#34;],
    &#34;time_resolution&#34;: &#34;TIME_RESOLUTION_15_MIN&#34;,
  },
  &#34;revision&#34;: 3,
  &#34;is_active&#34;: true,
  &#34;create_time&#34;: &#34;2025-01-01T00:00:00Z&#34;,
  &#34;update_time&#34;: &#34;2025-01-20T12:34:56Z&#34;
}

    Field Type Label Description
    market_location_ref MarketLocationRef Official market identifier for this Market Location
    market_location MarketLocation The logical Market Location (identity, jurisdiction, directions, resolution, etc.).
    revision uint64 Monotonically increasing revision counter.

    !!! note Each metadata change (e.g., supported_directions, market area, resolution, activation status) increments this counter. ListMarketLocations returns only the latest revision by default. | | is_active | bool | | Whether the Market Location is currently active.

    !!! note "Meaning of Activation Status" This flag indicates whether the Market Location is operationally active:

    • active = true - New samples MAY be ingested. - The location participates in billing, reconciliation, portfolio aggregation, and trading workflows.

    • active = false - No new samples may be ingested. - The location is excluded from operational workflows by default, but: ▪ historical samples remain fully accessible, ▪ historical revisions remain queryable, ▪ reactivation is possible without data loss.

    Deactivation represents an administrative state, NOT deletion. It preserves regulatory auditability and long-term metering integrity. | | create_time | google.protobuf.Timestamp | | Timestamp when this Market Location record was first created. | | update_time | google.protobuf.Timestamp | | Timestamp of the most recent metadata change. | | last_deactivated_time | google.protobuf.Timestamp | | Timestamp of the most recent deactivation event.

    !!! note Unset when the Market Location has never been deactivated. |

    MarketLocationId¤

    Market-standard identifier describing a Market Location.

    A Market Location is a jurisdiction-specific point of metering used for regulatory processes such as settlement, billing, supplier switching, balancing-group reconciliation, and DSO/TSO reporting. Different markets use incompatible identifier formats—varying in length, character sets, checksum rules, and decomposition.

    This message encapsulates the official, market-issued identifier used to reference such a point. Examples: • Germany: MaLo-ID (Marktlokations-ID) • UK: MPAN (Meter Point Administration Number) • US: ESI-ID (Electric Service Identifier) • Australia NMI (National Metering Identifier)

    !!! example "Example values for different markets" The following examples illustrate how the fields may be populated for different jurisdictions:

    | Market:Type     | Official ID         | Normalized Value
| --------------- | ------------------- | -----------------------------
| DE:MALO_ID      | &#34;12345678901&#34;       | &#34;12345678901&#34;
| UK:MPAN         | &#34;18 1066 1234 567 8901 234&#34; | &#34;18106612345678901234&#34;
| US_ERCOT:ESI_ID | &#34;10443720000012345&#34; | &#34;10443720000012345&#34;
| AU:NMI          | &#34;NEM1203456A&#34;       | &#34;NEM1203456A&#34;

In each case, `value` preserves the original format as provided by the
market operator, while `normalized_value` is an implementation-specific
cleaned representation suitable for validation, indexing, and
comparisons.
    Field Type Label Description
    value string Opaque identifier in its original market format as received from the source system (MSCONS, DataHub, CSV, manual entry, etc.).

    Examples: - "DE01234567890" (Germany MaLo) - "18 1066 1234 567 8901 234" (UK MPAN with spaces) - "NEM12-03456-A" (AU NMI with hyphens) | | type | MarketLocationIdType | | Identifies what type of official market identifier value represents. |

    MarketLocationRevisionSelection¤

    Field Type Label Description

    MarketLocationSample¤

    Represents a native metering sample submitted via upsert.

    Field Type Label Description
    sample_time google.protobuf.Timestamp Timestamp of the native reading (UTC).

    Interpretation depends on the metric type: • ENERGY: start of the interval. • POWER: reference timestamp (instantaneous or averaged). | | value | double | optional | Numeric value measured by the upstream meter.

    !!! note "Value for missing samples" When quality = DATA_QUALITY_MISSING, the value SHOULD be unset. | | quality | DataQuality | | Quality classification of the native reading. | | revision | uint64 | | Revision number used to correct previously ingested samples.

    Larger numbers represent newer revisions. A new revision replaces the previous one only for the same key tuple. |

    MarketLocationSampleDetail¤

    Represents a metering sample with additional metadata.

    This message represents two sample types: 1. Native samples — ingested at the meter’s original resolution. 2. Service-computed samples produced during resampling and/or aggregation.

    Field Type Label Description
    sample_time google.protobuf.Timestamp Timestamp associated with the sample.
    value double optional The numeric value, if available.

    !!! note "Missing value" This may be unset in the case the native reading was missing when quality = MISSING or if no native samples were present for the resampling window. | | quality | DataQuality | | Quality classification of the sample.

    For native samples this reflects the meter-provided quality. For resampled values this reflects the semantic quality of the aggregate. | | revision | uint64 | optional | Revision number for native samples.

    !!! note "Missing revision" For resampled values, this field is unset in case resampling combined multiple samples with different revisions. | | sample_update_time | google.protobuf.Timestamp | | Timestamp when the sample was last updated.

    !!! note "Timestamp interpretation" For native samples this represents the ingestion timestamp while for resampled values this indicates when the service computed the resampled interval window. | | resampling_method | ResamplingMethod | | How this sample was produced: native, downsampled, upsampled. |

    MarketLocationSamplesStreamFilter¤

    General filter criteria for querying samples uniformly apply to all Market Locations, directions, and metric types in this request.

    Field Type Label Description
    resampling_options ResamplingOptions Optional resampling options like resolution for the data, represented in seconds. If omitted, samples are returned at their original stored, native resolution.

    !!! note "Missing native samples" If a resampling interval contains no native samples, the service emits a sample with its value unset. | | revision_strategy | RevisionStrategy | | Optional revision-selection strategy applied when multiple revisions exist for the same timestamp. If unspecified defaults to the latest revision. For samples, the highest numeric revision value represents the newest version.

    Example: timestamp = 2025-01-01T00:00Z revisions: • rev 1 (MEASURED) • rev 2 (CORRECTED) • rev 3 (CORRECTED)

    • LATEST_ONLY → selects only rev 3 - ALL → selects rev 1, rev 2, rev 3

    !!! important "Effect on Resampling" When resampling is enabled, revision_strategy only determines which native revisions contribute to the aggregate, but the output always contains exactly one sample per interval. Late-arriving native samples may trigger corrected resampled values for past intervals. | | time_filter | TimeFilter | | Optional Time-filter defining the historical window and real-time behaviour of the stream.

    Semantics: • If end_time is provided, it MUST be ≤ the current server time. The server streams all samples t where start_time ≤ t < end_time and then closes the stream.

    • If end_time is omitted, the server streams all historical samples t ≥ start_time (if provided) and then continues streaming new samples in real time. The stream remains open indefinitely.

    • If start_time is omitted: – and end_time is omitted: the stream produces no historical data and begins streaming real-time samples only. – and end_time is provided: the historical window is empty and the stream closes immediately. |

    MarketLocationSeries¤

    Represents a semantic time series for a single logical Market Location.

    Field Type Label Description
    market_location_ref MarketLocationRef The enterprise and Market Location to which this sample belongs.
    direction EnergyFlowDirection Energy-flow direction of this series (IMPORT or EXPORT). Derived from the request and validated against supported_directions.
    metric_type MetricType Metric type represented by this series (e.g., ENERGY, POWER).

    MarketLocationsFilter¤

    Filters for selecting market locations.

    A Market Location must match all specified criteria to be included in the result.

    !!! note "Filter Semantics" • Each repeated field (e.g., market_location_id_filters) is evaluated using logical OR. • Different filter fields (if more are added in the future) will be combined using logical AND. • If no filters are provided, all Market Locations of the enterprise are returned.

    Field Type Label Description
    market_location_id_filters MarketLocationId repeated Optional filter to match one or more Market Locations by their official ID.

    Matching is performed using logical OR: If any listed identifier matches, the Market Location is included. | | activation_filter | ActivationFilter | | Optional filter for which activation states to include.

    !!! note "Default Behavior" By default, only active Market Locations are returned. |

    ReceiveMarketLocationSamplesStreamRequest¤

    Request for streaming time-series samples for one or more logical Market Locations.

    !!! note "Sample Series Expansion Logic" The server creates one independent time series for every unique combination of: • MarketLocationRef • EnergyFlowDirection • MetricType

    Example:
    2 Market Locations × 1 Direction × 2 Metrics = 4 series

Each of these is emitted as a separate MarketLocationSeries in the
streamed response.

    !!! example "Example Request" The following example requests ENERGY samples for two Market Locations, both in IMPORT direction, over a 24-hour window:

    ```json
{
  &#34;market_location_refs&#34;: [
    {
      &#34;enterprise_id&#34;: 42,
      &#34;market_location_id&#34;: {
        &#34;value&#34;: &#34;DE01234567890&#34;,
        &#34;type&#34;: &#34;MARKET_LOCATION_ID_TYPE_MALO_ID&#34;
      }
    },
    {
      &#34;enterprise_id&#34;: 44,
```

    ReceiveMarketLocationSamplesStreamResponse¤

    Streaming response containing one or more time series fragments.

    The service emits a distinct MarketLocationSeries message for every unique tuple of Market Location, EnergyFlowDirection and MetricType.

    The RPC is a finite server-side stream: once all samples matching the request (across all Market Locations, directions, and metric types) have been delivered, the server closes the stream. However, if the request’s time_filter specifies no end_time, the stream continues in real time.

    Consumers should treat each market location series in each streamed message as an independent, self-contained segment. Responses may be chunked.

    !!! note "Incremental / Chunked Streaming" The service may emit: • complete series in a single message, or • multiple incremental/chunked segments.

    !!! note "Sample Ordering & Updates" There is no guaranteed ordering between different series, between chunks of different series, or across series. A client MUST treat every received MarketLocationSeries as an independent, self-contained segment and merge or sort samples locally if ordering is required.

    The service may also emit more than one sample with identical
`sample_time`. This is normal and reflects the correction workflows
required in regulated metering and real-time resampling.

A sample may be re-emitted whenever the service obtains better or newer
information for that timestamp—whether through revised native readings,
delayed arrivals, or updated resampling intervals.

Clients MUST deduplicate samples for the same `sample_time` by:

  1. Prefer the sample with the highest revision, when revisions
     are present, otherwise
  2. Prefer the sample with the latest update_time.

This rule applies uniformly to both native and resampled streams.

    ResamplingOptions¤

    Resampling options for Market Location time-series data.

    Resampling allows clients to request a time resolution that differs from the Market Location’s native stored resolution. The service constructs a uniform output grid based on the requested resolution and produces exactly one sample per interval.

    Two semantic modes may result:

    • Downsampling (when the requested resolution is coarser) Multiple native samples fall into one output interval; these are combined using the selected aggregation method.

    • Upsampling (when the requested resolution is finer) Each native sample expands into multiple sub-intervals. ENERGY is allocated proportionally, while POWER is repeated stepwise.

    In both cases the output sample timestamp equals the start of the interval in the materialized grid.

    !!! example "Example: Downsampling from 1-minute to 15-minute intervals" The stored time series has a native resolution of Δt = 1 minute. Resampling is requested with a resolution of ΔT = 15 minutes. In this case all native samples whose timestamps fall within an interval [t, t + Δt) contribute to the aggregated value for that interval. The timestamp of the aggregated sample is exactly t, the start of the interval.

    For each interval k:
    Ik = [T0 &#43; k·ΔT,  T0 &#43; (k&#43;1)·ΔT)

The aggregated value A_k is the arithmetic mean of all samples whose
timestamps ts satisfy: ts ∈ Ik

The resampled series consists of points:
    (t = T0 &#43; k·ΔT,  value = A_k)

    !!! example "Upsampling: 15-minute → 5-minute" If the native resolution is Δt = 15 min and the requested resolution is ΔT = 5 min, each native interval expands into three equally sized sub-intervals, with ENERGY proportionally allocated and POWER repeated.

    Field Type Label Description
    resolution TimeResolution Optional resampling resolution for the output time series.
    downsampling_method DownsamplingMethod Optional aggregation method applied when downsampling. Defaults to DOWNSAMPLING_METHOD_MEAN when omitted.

    UpsertMarketLocationSamplesStreamRequest¤

    A single ingestion event for one Market Location sample.

    Each request message processes exactly one sample and produces one acknowledgement response.

    The server performs strict validation of: • timestamp alignment with the Market Location's contractual resolution, • energy-flow direction against supported_directions, • metric_type against supported metrics, • metric_unit consistency with metric_type, • revision monotonicity for the (ML, direction, metric, timestamp) tuple.

    !!! important "Correction via revisioning (no deletion)" The MarketMeteringService never deletes samples. Regulated metering processes require a full historical audit trail.

    A previously ingested sample is corrected by submitting a new revision
with the same sample_time but a higher revision value.

Typical patterns:
  • Invalidate a value → send a new revision with
    `quality = DATA_QUALITY_MISSING` and value = 0.
  • Correct a value    → send a new revision with the corrected value
    and `quality = DATA_QUALITY_CORRECTED`.

The backend selects the highest revision when serving data, while older
revisions remain queryable via revision strategies.

    !!! warning "Timestamp alignment is mandatory" sample.sample_time MUST align with the Market Location's contractual time_resolution.

    Example:
  time_resolution = PT15M → allowed times are:
    00:00, 00:15, 00:30, 00:45, ...

Misaligned timestamps are rejected.

    !!! warning "Metric-unit consistency is validated" The provided metric_unit MUST be compatible with metric_type. ENERGY → {Wh, kWh, MWh} POWER → {W, kW, MW} REACTIVE_ENERGY → {VArh, kVArh, MVArh} REACTIVE_POWER → {VAr, kVAr, MVAr}

    The backend does not perform unit conversion.

    !!! warning "Direction and metric must be allowed" direction MUST be present in the Market Location's supported_directions. metric_type MUST be supported for ingestion by the service.

    METRIC_UNIT_VAR 30 Volt-ampere-reactive (VAr): Base unit for instantaneous reactive power.
    METRIC_UNIT_KVAR 31 Kilovolt-ampere-reactive (kVAr): Standard unit for reactive power in distribution networks and large commercial installations.

    ResamplingMethod¤

    Indicates how a returned sample was derived relative to the originally stored metering resolution.

    Name Number Description
    RESAMPLING_METHOD_UNSPECIFIED 0 UNSPECIFIED: Default — should not appear in valid API responses.
    RESAMPLING_METHOD_NATIVE 1 NATIVE: The sample is stored at this exact resolution in the backend.
    RESAMPLING_METHOD_DOWNSAMPLED 2 DOWNSAMPLED: The sample is computed from finer-granularity data. Example: native = 1 min; requested = 15 min.
    RESAMPLING_METHOD_UPSAMPLED 3 UPSAMPLED: The sample is computed from coarser-granularity data. Example: native = 15 min; requested = 5 min.

    !!! important Upsampling cannot create new information. Values are typically distributed (for energy) or repeated/interpolated (for power). |

    RevisionStrategy¤

    Strategy for selecting which revisions of a resource should be returned.

    Many entities in regulated energy systems evolve over time and may exist in multiple historical revisions. Examples include: • time-series samples that receive corrections or late updates • Market Location metadata updated by the user or backend processes

    This enum allows clients to control whether they want only the most recent version of each entity or the full revision history.

    !!! note "Revision ordering" Revisions are ordered strictly by their numeric revision field. The service does not infer semantics from market-specific document types or timestamps — the highest numeric revision always represents the newest version of a given entity.

    Name Number Description
    REVISION_STRATEGY_UNSPECIFIED 0 UNSPECIFIED: Should not be used. Defaults to LATEST_ONLY.
    REVISION_STRATEGY_LATEST_ONLY 1 LATEST_ONLY: Return only the newest revision of each entity.

    !!! note The newest revision is determined solely by the highest numeric revision value. | | REVISION_STRATEGY_ALL | 2 | ALL: Return every available revision of each entity.

    !!! note Consumers must handle multiple entries representing the same logical entity or timestamp, differentiated only by revision number. |

    TimeResolution¤

    Defines the time resolution (sampling interval) of metering data.

    All timestamps refer to the start of the measured interval, and the interval runs until: [timestamp, timestamp + resolution)

    Resolutions are modeled explicitly because different markets use different fixed intervals.

    !!! example "Common resolution examples" These intervals are commonly encountered in interval metering systems worldwide:

    | Jurisdiction        | Metric Type      | Resolution
|---------------------|------------------|------------
| Germany (MaLo)      | Energy (kWh)     | PT15M
| UK (MPAN)           | Energy (kWh)     | PT30M
| Australia (NEM12)   | Energy (Wh)      | PT5M
| US (ERCOT)          | Power (kW)       | PT5M
| US (PJM/ISO-NE)     | Power/Energy     | PT1H
| Smart meters (AMI)  | Energy           | PT1M

    !!! note "Primary Resolution" A Market Location typically has one primary contractual resolution. Some systems may support additional resolutions (e.g., for telemetry or submetering).

    Name Number Description
    TIME_RESOLUTION_UNSPECIFIED 0 UNSPECIFIED: Must not be used.
    TIME_RESOLUTION_1_MIN 1 PT1M: 1-minute interval. Used in some modern AMI systems (US, AU) and for high-frequency metering.
    TIME_RESOLUTION_2_MIN 2 PT2M: 2-minute interval. Rare, but supported by some industrial submetering systems.
    TIME_RESOLUTION_5_MIN 3 PT5M: 5-minute interval. Used in Australia (AEMO NEM12), US ISOs (ERCOT), and many AMI systems.
    TIME_RESOLUTION_10_MIN 4 PT10M: 10-minute interval. Seen in some Asian and utility-specific formats.
    TIME_RESOLUTION_15_MIN 5 PT15M: 15-minute interval. Standard for Germany (MSCONS), Switzerland, Italy, Netherlands, and future Nordic harmonization.
    TIME_RESOLUTION_30_MIN 6 PT30M: 30-minute interval. Historic UK settlement period; still widely used for MPAN half-hourly data.
    TIME_RESOLUTION_60_MIN 7 PT60M: 60-minute interval (1 hour). Nordic ElHub standard; common in US and Canadian utilities.
    TIME_RESOLUTION_1_DAY 8 P1D: Daily resolution. Used for coarse-granularity reporting or legacy billing schemas.

    MarketMeteringService¤

    Metering data ingestion is performed using the bidirectional stream Each message carries a single metering value together with its metadata, and corrections are applied by submitting a new sample for the same timestamp and a higher revision. The service never deletes or overwrites earlier revisions; instead, each correction creates an immutable audit trail.

    5. Retrieve historical and real-time metering data

   Depending on the time filter, the service may return a finite
   historical dataset, continue seamlessly into real-time mode once
   historical samples are exhausted, or stream only real-time
   measurements if no start_time is provided. Optional resampling
   may be applied to request coarser intervals; in this mode,
   late-arriving native samples can trigger corrected resampled
   outputs for previously emitted windows.

Together, these operations form a complete lifecycle for managing,
correcting, and streaming billing-grade metering data across global
electricity markets.

    !!! important "Authentication" All requests to MarketMeteringService must be signed. The key identifier and signature must be included in the request metadata (gRPC metadata / HTTP headers). The signature must be computed using the HMAC-SHA256 algorithm and secret key. All requests to this service must be made over TLS (HTTPS).
